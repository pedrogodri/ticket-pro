# F1 Plataforma — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cada linguagem ganha a camada de plataforma de mensageria confiável:

- envelope e validação contra `contracts/`;
- outbox + relay;
- consumidor idempotente com classificação e DLQ;
- backoff, logging e propagação de trace.

A plataforma é provada por testes de integração de R1 e R6. Ao final, os 8 serviços sobem `healthy`, com banco, migrations Flyway e readiness real.

**Architecture:** Há uma especificação única de plataforma (seção *Platform contract*), implementada 4 vezes:

| Onde | Como |
|---|---|
| `shared/go` | Vendorizado em inventory e notification |
| `shared/dotnet` | Vendorizado em payment e user |
| `auth-service/.../platform` (Java) | Próprio do serviço |
| `order-service/src/platform` (TS) | Próprio do serviço |

A mesma matriz de testes P1–P15 roda em todas. O `scripts/sync-shared.sh` copia libs e contratos para os serviços (ADR-0017).

Cada serviço com estado ganha:

- o próprio Postgres numa rede `<svc>-data`, isolada dos outros serviços;
- um job `<svc>-migrate` (Flyway) com roles `owner/app/worker` e as tabelas `outbox`/`processed_messages`;
- `/health/ready` com `db` e `broker`.

## Global Constraints

- **Branch:** `feat/f1-platform`, criada a partir de `feat/f0-foundation`. Nunca commitar na `main`, sem push, sem worktree.
- **Dependências:** versão estável mais recente com ≥ 2 semanas, travada no lockfile (`go.sum`, `packages.lock.json`, `pom.xml` com versão explícita, `package-lock.json` gerado com o npm do Node 22).
- **Imagens:** `postgres:16-alpine`, `ministackorg/ministack:1.5.40` (também nos testes). A tag fixa de `flyway/flyway` é escolhida na Task 2 e reutilizada por todos os serviços.
- **Envelope:** exatamente `messageId, correlationId, type, version, occurredAt, payload`. `occurredAt` é RFC 3339 UTC com milissegundos (`2026-11-20T18:30:12.345Z`). `messageId` é UUID v7 onde houver API estável, senão v4 (RFC 0001 decisão 8).
- **Atributos SNS:** `type`, `version`, `correlationId` e `traceparent`, todos `DataType=String`. O `traceparent` é **omitido** quando vazio, porque o SNS rejeita atributo String vazio.
- **Backoff:** `delay(n) = random(0, min(cap, base·2^n))`, com `base = 200 ms` e `cap = 30 s`.
- **SDK AWS:** retry interno com 1 tentativa (`max_attempts=1`) e timeout HTTP `HTTP_CLIENT_TIMEOUT_MS` (padrão 3000).
- **Env novas** (com padrão, listadas no `.env.example` de cada serviço que as usa):

  | Variável | Padrão |
  |---|---|
  | `OUTBOX_POLL_INTERVAL_MS` | 200 |
  | `OUTBOX_BATCH_SIZE` | 50 |
  | `OUTBOX_MAX_BACKOFF_MS` | 30000 |
  | `OUTBOX_CLAIM_LEASE_MS` | 30000 |
  | `SQS_WAIT_TIME_S` | 10 |
  | `SQS_MAX_RECEIVE_COUNT` | 3 |
  | `CONSUMER_CONCURRENCY` | 4 |
  | `HTTP_CLIENT_TIMEOUT_MS` | 3000 |

  `DATABASE_URL` e `DATABASE_WORKER_URL` são obrigatórias nos serviços com banco. `<DOMAIN>_TOPIC_ARN` é obrigatória nos que publicam.
- **Bancos** (padrões §3, §6.1):

  | Serviço | Container / banco | Roles | Publica (outbox) |
  |---|---|---|---|
  | auth-service | `auth-db` / `auth` | `auth_owner/_app/_worker` | sim (`AUTH_TOPIC_ARN`) |
  | user-service | `users-db` / `users` | `users_*` | sim (`USERS_TOPIC_ARN`) |
  | order-service | `orders-db` / `orders` | `orders_*` | sim (`ORDERS_TOPIC_ARN`) |
  | inventory-service | `inventory-db` / `inventory` | `inventory_*` | sim (`INVENTORY_TOPIC_ARN`) |
  | payment-service | `payments-db` / `payments` | `payments_*` | sim (`PAYMENTS_TOPIC_ARN`) |
  | notification-service | `notifications-db` / `notifications` | `notifications_*` | não (só `processed_messages`) |
  | gateway, autoscaler | — | — | — |

- **Migrations** (texto idêntico em todo serviço, trocando só o prefixo):
  - `V0001__create_roles.sql`: `<db>_app` (LOGIN, sem BYPASSRLS) e `<db>_worker` (LOGIN, BYPASSRLS), com senhas via placeholders Flyway `${appPassword}` / `${workerPassword}`. Inclui `ALTER DEFAULT PRIVILEGES` (DML em tabelas e `USAGE, SELECT` em sequências para app e worker).
  - `V0002__create_outbox.sql`: o DDL de padrões §6.2, verbatim. O notification não tem este arquivo.
  - `V0003__create_processed_messages.sql`: o DDL de padrões §6.2, verbatim. No notification, o arquivo se chama `V0002__…`.
- **Owner:** `<db>_owner` é o `POSTGRES_USER` do container (superusuário, só desenvolvimento). O Flyway conecta com ele.
- **Senhas de banco:** no `.env.example` do próprio serviço, marcadas "DEVELOPMENT ONLY".
- **Rede de dados:** o Postgres fica **só** em `ticketpro-<svc>-data`. O serviço e o seu migrate ficam em `backend` + `<svc>-data`. Nenhum banco publica porta.
- **Health** (RFC 0003 §5.9):
  - `/health/live` → `200 {"status":"up"}`.
  - `/health/ready` → `200 {"status":"up","checks":{"db":"up","broker":"up"|"degraded"}}`.
  - Com o banco fora, `/health/ready` → `503 {"status":"down","checks":{"db":"down",…}}`.
  - `broker` só aparece em quem roda relay. Gateway e autoscaler mantêm `checks:{}`.
- **Vendorizado:** `internal/platform/`, `src/<Proj>/Platform/` e `contracts/` dentro de um serviço nunca são editados à mão.
- **Commits:**
  - Conventional, com escopo da pasta (`feat(shared): …`, `feat(inventory-service): …`).
  - Sync em commit próprio (`chore(<svc>): sync shared go v0.1.0`).
  - Todo commit termina com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Platform contract (igual nas 4 linguagens)

Nomes abaixo em Go. As outras linguagens usam o equivalente idiomático, e as Tasks 7, 11 e 13 listam os nomes exatos.

| Módulo | API | Semântica |
|---|---|---|
| `retry` | `Delay(attempt int, base, cap time.Duration, rnd func() float64) time.Duration` | Full jitter. `rnd ∈ [0,1)`. `attempt` começa em 0. |
| `envelope` | `type Envelope struct{MessageID, CorrelationID, Type string; Version int; OccurredAt time.Time; Payload json.RawMessage}`; `New(correlationID, typ string, version int, payload any) (Envelope, error)`; `(Envelope) MarshalJSON` | `New` gera `messageId` e `occurredAt = now UTC` truncado em ms. O JSON tem exatamente 6 chaves. |
| `envelope` | `Unwrap(body []byte) (Envelope, error)` | Corpo com `"Type":"Notification"` + `"Message"` → parse de `Message`. Senão, o corpo é o envelope. Qualquer falha retorna erro que satisfaz `errors.Is(err, ErrPoison)`. |
| `envelope` | `NewValidator(contractsDir string) (*Validator, error)`; `(*Validator) Validate(raw []byte) error` | Carrega todo `*.schema.json` do diretório, registrado pelo `$id` (os `$ref` relativos resolvem contra o `$id`). Escolhe `events/<type>/v<version>.schema.json`. `type`/`version` sem schema → `ErrUnsupportedVersion`. Schema violado → `ErrInvalidMessage`. Os dois são `ErrPoison`. |
| `tracing` | `Inject(ctx) string`; `Extract(ctx, traceparent string) context.Context` | Propagador W3C TraceContext. `Inject` sem span ativo → `""`. |
| `logging` | `New(w io.Writer, service string, level slog.Level) *slog.Logger`; `WithCorrelationID(ctx, id) context.Context` | Chaves de padrões §5. O handler acrescenta `correlationId`, `traceId` e `spanId` do contexto quando existem. |
| `idempotency` | `Record(ctx, tx pgx.Tx, consumer, messageID string) (fresh bool, err error)` | `INSERT … ON CONFLICT DO NOTHING`. `fresh = (linhas afetadas == 1)`. |
| `outbox` | `Enqueue(ctx, tx pgx.Tx, topicARN string, env envelope.Envelope) error` | Insere na TX do chamador e grava `traceparent = tracing.Inject(ctx)` (NULL se vazio). |
| `outbox` | `type Publisher interface{ Publish(ctx, topicARN string, env envelope.Envelope, traceparent string) error }` | |
| `outbox` | `NewRelay(RelayConfig) *Relay`; `(*Relay) RunOnce(ctx) (published int, err error)`; `(*Relay) Run(ctx) error`; `(*Relay) BrokerUp() bool` | Algoritmo abaixo. |
| `messaging` | `NewSNSPublisher(client *sns.Client) *SNSPublisher` (implementa `Publisher`); `NewAWSConfig(ctx, timeout time.Duration) (aws.Config, error)` | Atributos conforme Global Constraints. `RetryMaxAttempts = 1`. |
| `messaging` | `type Handler interface{ Versions() []int; Handle(ctx, tx pgx.Tx, env envelope.Envelope) error }`; `ErrStale` | `Handle` retorna `nil` (sucesso), `ErrStale` (transição inválida), erro que satisfaz `ErrPoison` (venenosa) ou outro erro (transitória). |
| `messaging` | `NewConsumer(ConsumerConfig) *Consumer`; `(*Consumer) Process(ctx, msg sqstypes.Message) Outcome`; `(*Consumer) Run(ctx) error`; `(*Consumer) BrokerUp() bool` | `Outcome ∈ {Succeeded, Duplicate, Stale, Poison, Transient}`. |

**Relay (`RunOnce`):**

1. Faz o claim numa TX curta, sem rede:

   ```sql
   UPDATE outbox SET next_attempt_at = now() + lease
   WHERE id IN (SELECT id FROM outbox
                WHERE published_at IS NULL AND next_attempt_at <= now()
                ORDER BY id LIMIT $batch FOR UPDATE SKIP LOCKED)
   RETURNING *
   ```

2. Publica cada linha **fora** de TX, na ordem de `id`:
   - **Sucesso:** `published_at = now(), last_error = NULL` e log `message_published`.
   - **Falha:** `attempts = attempts+1`, `next_attempt_at = now() + Delay(attempts)` (cap `OUTBOX_MAX_BACKOFF_MS`) e `last_error`. As linhas restantes do lote voltam a `next_attempt_at = now()`, sem incrementar `attempts`, e o lote para.
3. Uma linha por transição de estado do broker: `broker_down` / `broker_up`.

**`Run`:** chama `RunOnce`. Espera `OUTBOX_POLL_INTERVAL_MS` após sucesso, ou `Delay(falhas consecutivas)` após falha. Termina limpo no cancelamento do contexto.

**Consumer (`Process`), conforme RFC 0003 §5.4:**

1. `Unwrap` + `Validate`. Falha → `Poison`.
2. Busca o handler por `type`:
   - sem handler → `Poison`;
   - `version ∉ Versions()` → `Poison` (log `unsupported_version`).
3. `ctx = Extract(atributo traceparent)` e `WithCorrelationID(env.correlationId)`.
4. Abre `BEGIN` no pool **worker** e chama `Record(consumer, messageId)`. Se a mensagem não é nova: rollback, `DeleteMessage`, log `duplicate=true` → `Duplicate`.
5. Chama `Handle` e decide pelo retorno:

   | Retorno | Ação | Outcome |
   |---|---|---|
   | `nil` | commit → `DeleteMessage` → log `message_consumed` | `Succeeded` |
   | `ErrStale` | commit (o registro fica) → `DeleteMessage` → log `stale_event` | `Stale` |
   | erro que satisfaz `ErrPoison` | rollback → `ChangeMessageVisibility(0)` → log `poison=true` | `Poison` |
   | outro erro | rollback → `ChangeMessageVisibility(Delay(receiveCount) em s, mínimo 1)` | `Transient` |

**`Run`:** `ReceiveMessage` com `MaxNumberOfMessages = CONSUMER_CONCURRENCY`, `WaitTimeSeconds = SQS_WAIT_TIME_S`, atributos `ApproximateReceiveCount` e todos os de mensagem. As mensagens do lote são processadas em paralelo. Erro de receive → espera `Delay(n)`, e `n` zera no primeiro sucesso. Nunca há ack antes do commit.

### Matriz de testes da plataforma (P1–P15)

Cada implementação (Tasks 3–4, 7–8, 11, 13) tem **um teste por linha**, com o ID no nome (Go `TestP09_DuplicateFiveTimesHasOneEffect`, C# `P09_DuplicateFiveTimesHasOneEffect`, Java `p09DuplicateFiveTimesHasOneEffect`, TS `"P09 duplicate five times has one effect"`).

Os testes de integração usam:

- Testcontainers `postgres:16-alpine`, com o fixture `platform.sql` = DDL de padrões §6.2 + `CREATE TABLE effects (id bigserial PRIMARY KEY, message_id uuid NOT NULL, note text)`;
- `ministackorg/ministack:1.5.40` (porta 4566), com o mesmo probe de saúde de `infra/compose/compose.yaml`.

O broker "parado" é `docker pause <containerId>` / `docker unpause`, via CLI, igual nas 4 linguagens. O handler de teste insere 1 linha em `effects`.

| ID | Tipo | Cenário | Asserções |
|---|---|---|---|

## Review Focus

1. **Broker fora no boot do serviço.** O processo sobe, `/health/live` = 200, `/health/ready` = 200 com `broker:"degraded"` depois da 1ª falha do relay, e o `POST` continua aceitando requisições (gravação no outbox). Teste de readiness com relay fake `BrokerUp()=false` em cada serviço publicador (Tasks 5, 9, 10, 12, 14).
2. **Banco fora.** `/health/ready` = 503 com `db:"down"` e `/health/live` = 200. Teste com pinger fake que falha em cada serviço com banco (Tasks 5, 6, 9, 10, 12, 14).
3. **`traceparent` vazio enviado ao SNS.** O SNS rejeita o publish e o relay ficaria preso em retry eterno. Coberto por P12 (linhas sem traceparent publicam).
4. **Cópia vendorizada adulterada ou obsoleta.** O `sync-shared.sh --check` falha quando:
   - um arquivo vendorizado foi editado à mão;
   - um arquivo foi removido da origem e continua no destino;
   - o `VERSION` da origem mudou sem novo sync.

   Rodar o sync duas vezes não gera diff. Testes na Task 1.
5. **Deriva do DDL de plataforma entre os 6 bancos e o fixture.** `scripts/verify-platform.sh` compara as colunas de `outbox`/`processed_messages` (via `information_schema.columns`) entre os bancos, e o RLS/BYPASSRLS dos roles. Task 2, executado de novo na Task 15.
